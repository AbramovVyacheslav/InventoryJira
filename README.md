# Инвентаризация Jira

Мобильное приложение для терминалов сбора данных (ТСД) на Android (Urovo DT50 и аналоги) и обычных смартфонов. Физическая инвентаризация, перемещение и экспресс-проверка ИТ-оборудования и офисной техники с прямой интеграцией в **Jira Assets** и **Jira Service Management** по REST API — без промежуточных серверов и баз данных на стороне организации.

## Возможности

- **Авторизация в Jira** (логин/пароль корпоративной учётной записи, AD синхронизирован на стороне Jira).
- **Полностью автономная локальная БД** (Drift / SQLite) на ТСД: инвентаризацию можно прерывать и переносить на дни (ушёл на выходные — продолжил в понедельник без потери данных).
- **Актуальный срез из Jira Assets**: при старте новой инвентаризации старые результаты очищаются, технику/помещения/сотрудников приложение скачивает из Assets.
- **Динамические атрибуты**: структура полей запрашивается из Jira Assets; новые реквизиты подхватываются без изменения кода.
- **Инвентаризация помещения**: QR на двери кабинета → список техники из локальной БД; сквозной поиск (код 1С / серийник / название); фильтр «Только расхождения»; «своё» оборудование помечается проверенным и получает «Дату последней инвентаризации» (локально + в Jira); пустое МОЛ блокируется обязательным окном выбора сотрудника; «чужая» техника перемещается в текущий кабинет + фоновая заявка на перемещение в Jira Service Management; пакетная печать этикеток отмеченных позиций прямо во время сессии.
- **Офлайн-устойчивость**: при падении Wi-Fi заявки копятся в локальной `SyncQueue` и автоматически отправляются при восстановлении сети; экран «Монитор синхронизации» показывает статистику и позволяет выгрузить очередь вручную.
- **Экспресс-проверка**: карточка актива с полными атрибутами Jira, смена состояния (Работает / Требует ремонта / Повреждено / Новое), необязательное фото дефекта (вложение к заявке JSM, не блокирует сохранение), заявка «Было → Стало» при любых правках.
- **Промышленный UX**: звуковой/вибро-отклик «вслепую» (успех — высокий пик + короткая вибрация, перемещение — двойной сигнал + двойная вибрация, ошибка/дубликат/пустой МОЛ — низкий тон + вибрация 1 с); крупные кнопки; цветовая кодировка (зелёный — проверено, серый — осталось, оранжевый — чужая техника, красный — ошибка); блокировка выхода из инвентаризации диалогом; сервисная панель: батарея, очередь пакетов, статус принтера.
- **Печать этикеток 58×30 мм** на TSC TE210 по Wi-Fi (TSPL, TCP/9100). Слева QR (ключ объекта), справа — название, ключ, код 1С, организация.
- **Сканер ТСД** через Android Broadcast Intents (Urovo / Zebra / Honeywell / Chainway) + камера на смартфонах.

## Что сознательно НЕ входит (ограничение затрат)

- Нет прямой интеграции с 1С — Код1СБУ берётся транзитом через Jira Assets.
- Нет функционала списания/утилизации (только веб-интерфейс Jira).
- Нет галерей/альбомов — одно необязательное фото дефекта.

### Локальная БД (Drift)

Таблицы: `AppSettings` (одна строка конфигурации, не сбрасывается при перезапуске), `Assets` (снимок Jira + локальные флаги проверки), `Rooms`, `Employees`, `SyncQueueItems` (очередь отправки: `pending|sending|failed|sent`), `InventorySessions` (сессии инвентаризации, позволяют прерываться на дни).

Схема версионируется (`schemaVersion = 1`); при изменении таблиц добавляйте миграцию в `MigrationStrategy` и перегенерируйте код.

## Быстрый старт (машина с Flutter SDK)

Требования: **Flutter ≥ 3.19** (стабильный), Dart ≥ 3.3, Android Studio или Android SDK (cmdline-tools) и JDK 17.

```bash
git clone <repo> && cd InventoryJira

# 1) Gradle-скаффолдинг и скрипты (в репозитории нет gradle-wrapper.jar —
#    он подкладывается командой ниже; существующие файлы НЕ перезаписываются):
flutter create --platforms=android --org com.inventoryjira .

# 2) Зависимости + генерация кода Drift (app_database.g.dart):
flutter pub get
dart run build_runner build --delete-conflicting-outputs

# 3) Анализ и тесты:
flutter analyze
flutter test

# 4) Запуск на подключённом ТСД/смартфоне:
flutter run
```

### Сборка APK

```bash
flutter build apk --release
# build/app/outputs/flutter-apk/app-release.apk
```

⚠️ Перед выпуском подпишите сборку собственным ключом: создайте `android/key.properties` (в `.gitignore`) и `release`-секцию `signingConfig` в `android/app/build.gradle`. Сейчас `release` подписывается debug-ключом, чтобы APK можно было собрать «из коробки».

Проверка на Urovo DT50: установите APK (`adb install` или по QR/MDM), включите DataWedge-профиль или встроенный режим «Broadcast Intent» с действиями из `MainActivity.kt` (см. «Сканер» ниже).

## Настройка Jira (один раз, администратором)

1. **Сервисный аккаунт** с правами: Browse Assets / Object schemas, Create/Edit objects, и «SD Agent» (или клиенту JSM — если хотите видеть заявки). Для Jira Cloud — API token (https://id.atlassian.com/manage-profile/security/api-tokens); для Jira Server/Data Center — Personal Access Token (PAT) или пароль, если PAT отключён.
2. **ID схемы объектов** (Object Schema ID): Assets → Schemas → шестерёнка (⚙) → *Schema ID* (число). Его вводят в «Настройки → Jira API → ID схемы объектов».
3. **Jira Service Management**: проект JSM должен содержать типы заявок «Перемещение» и «Изменение данных» (или аналоги). Их **Request Type ID** и **Service Desk ID** вводятся в «Настройки → Jira Service Management».
4. **Атрибуты Assets** (см. «Динамические атрибуты»):
   - У активов: серийный номер, код 1С, организация, состояние, «Дата последней инвентаризации» (тип **Date**), ссылки на «Помещение» и «Пользователь (МОЛ)».
   - У помещений: имя + атрибут-штрихкод (значение QR-наклейки на двери, например `ROOM-101`).
   - У сотрудников: имя + e-mail.

### Как устроен «снимок»

`AssetRepository.downloadSnapshot` скачивает ВСЕ объекты схемы (AQL `objectSchemaId=<id>`, пагинация по 100) и раскладывает по типам эвристикой:

- есть атрибут с e-mail → **сотрудник**;
- есть серийник / код 1С / ссылка на помещение / ссылка на МОЛ → **актив**;
- иначе → **помещение**.

Если у вас несколько схем или классификация отличается — поправьте эвристику в `downloadSnapshot` (8 строк) или введите отдельные AQL-запросы по типам объектов.

### Динамические атрибуты

Все атрибуты объекта хранятся локально как JSON (`Assets.attributesJson`) и целиком показываются в карточке актива. Известные реквизиты распознаются по русским/английским именам атрибутов (списки-кандидаты в `lib/data/jira/attribute_mapper.dart`): `Серийный номер|Serial|Заводской номер`, `Код 1С|Code1C|1СБУ`, `Организация|Organization`, `Помещение|Кабинет|Room|Location`, `Пользователь (МОЛ)|МОЛ|User`, `Состояние|Статус|Status`, `Дата последней инвентаризации|Last Inventory`. Новые атрибуты, добавленные в Jira, подтянутся автоматически — просто откройте карточку.

## Сканер ТСД (Urovo DT50)

На ТСД сканер работает в режиме Broadcast Intent (мгновенное считывание без камеры). Встроенный лазер DT50 по умолчанию шлёт `android.intent.action.SCANRESULT` с extra `data`. `MainActivity.kt` ловит дополнительные форматы (Zebra DataWedge `com.symbol.datawedge.data_string`, Honeywell, Chainway, Urovo `urowo.intent.action.SCAN`) и передаёт код во Flutter по MethodChannel `inventory_jira/scanner` → `ScannerService.scanStream`.

Если у вашего устройства другая нотификация — добавьте action/extra в списки `scanActions` / `extraKeys` в `MainActivity.kt`. На обычных смартфонах и при неработающем лазере используйте режим камеры (кнопки с иконкой QR).

Также поддерживается **keyboard-wedge** (сканер как клавиатура + Enter): ввод попадает в строку поиска инвентаризации, Enter → `onSubmitted` обрабатывает код.

## Принтер TSC TE210 (TSPL)

Этикетка 58×30 мм @203 dpi = 463×240 точек. Слева QR (ключ объекта Jira), справа четыре строки (название, ключ, код 1С, организация). Печать — напрямую `Socket.connect(ip, 9100)`, TSPL-команды (`SIZE/GAP/CODEPAGE/QRCODE/TEXT/PRINT`). Кириллица: `CODEPAGE UTF-8` (прошивки E/1/4+) или `Windows-1251` (старые прошивки — переключатель в настройках; символы кодируются `Cp1251`).

«Тестовая печать» в настройках отправляет этикетку `TEST PRINT`. Зелёный/красный индикатор принтера в сервисной панели — результат последней попытки (печать / проверка связи).

## Офлайн и очередь синхронизации

Операции, требующие Jira (заявка на перемещение, заявка «Было/Стало» + вложение, обновление атрибута «Дата инвентаризации»), не блокируют сканирование: они складываются в `SyncQueueItems` с типом `move | assetChange | inventoryDate` и JSON payload'ом. `SyncEngine` отправляет очередь:

- при восстановлении сети (Connectivity stream);
- периодически раз в 60 секунд;
- вручную через «Монитор синхронизации → Отправить сейчас».

Ошибочные записи помечаются `failed` с `retryCount++` и `lastError`; успешные — `sent` (+ `jiraIssueKey`). Повторная отправка — той же кнопкой.

## Технические логи

`<ApplicationDocuments>/logs/app.log` (+ `app.log.1..5` при ротации, 1 МБ каждый). Пишет: старт/открытие БД, скачивание снимка (сколько объектов), постановка в очередь, ошибки отправки, отсутствие атрибута «Дата инвентаризации» у актива. Аудит пользовательских действий ведётся штатными средствами Jira (история объекта Assets, заявки JSM).

## Разработка

```bash
dart run build_runner build --delete-conflicting-outputs   # после правок app_database.dart
flutter test                                               # юнит-тесты
flutter analyze
```

- При добавлении поля в `app_database.dart` — поднимайте `schemaVersion` и дописывайте миграцию.
- Новые типы записей в очередь — расширяйте `SyncPayloads` + `SyncEngine._sendOne` и добавляйте тест.
- CI (GitHub Actions, `.github/workflows/ci.yml`): pub get → build_runner → analyze → test → сборка release APK (артефакт).

## Известные ограничения

- Снимок скачивается из одной схемы; мультисхемные AD-окружения требуют доработки `AssetRepository.downloadSnapshot`.
- Классификация объектов по схеме — эвристика (см. «Как устроен снимок»).
- Дата инвентаризации пишется в Jira асинхронно; если атрибут не найден по списку кандидатов, локальное обновление всё равно выполняется, Jira-обновление пропускается (пишется WARN в лог).
- Экранные маски принтеров кроме TE210 не тестировались.
